## 1. 目的と成功条件

### 1.1 目的

ミラーレス派ユーザー（当面はオーナー本人）が、週次・イベント単位の写真群に対して、

1. AI の候補提案を手がかりに短時間で「残す／残さない」を決め、  
2. 外部現像した画像をオリジナルとは別に **作品** として取り込み、  
3. 既存の Lumina Notes（カード・分析ログ）と紐づけて **対話痕跡** を残す  

ことで、あとから未来の自分が読み返せる素材を蓄積する。

北極星のうち、本仕様が担うのは主に **深い輪（あとからの振り返り）** 側である。  
中心にある往復（残す→見返す→言葉にする→もう一度見る）を、週／イベントの単位で回せるようにする。

### 1.2 縮約の目安

| 単位 | 入力の目安 | 確定の目安 |
|------|------------|------------|
| 週 | 約 200 枚 | 約 20 枚 |
| 月／イベント | 約 400 枚 | 約 40 枚 |

比率は厳密な上限ではなく、**およそ 1/10** の感触をガイドとする。AI は迷い枠を優先度付きで多めに出してよい。最終枚数は人が決める。

### 1.3 成功条件（R1′-A）

オーナーが、イベントフォルダ（例: 約 400 枚）に対して次を **日常操作として一通り完了**できる。

1. 候補が提示される（コア案 ＋ 迷い枠）  
2. 人が確定・回収・却下できる  
3. 確定分を作品として取り込める（オリジナル非破壊）  
4. 作品にカード／Markdown ノート／ログが紐づく  
5. 提案と確定の差分が後から参照できる形で残る

## 2. ユーザーストーリー

### US-1 週末の短絡

週末、ミラーレスで撮った週の写真（およそ 200 枚）が入ったフォルダを開く。AI が「立ち止まれそうなコマ」を提案する。自分で見て残す・外す・漏れた一枚を回収し、およそ 20 枚に整える。

### US-2 イベント後の作品化

旅行イベント `YYYYMMDD_短い名前` のフォルダで同様に短絡する。DxO 等で現像した JPEG を、確定したコマの作品として取り込む。撮って出しのまま残すコマもある。

### US-3 言葉と痕跡

作品ごとに、AI が言語化した文を見る。納得しなくても「そう思う／そうではない」と感じる。必要なら自分のコメントやキーワードを足す。既存の講評カードと分析ノートが作品に紐づく。

### US-4 あとから読み返す準備

短絡結果・作品・カード／ログ・差分が、同じ月／イベントの配下に残り、将来の章やレポート（R1′-B/C）の素材になる。

## 3. 対象範囲／非対象

### 3.1 スライス

| スライス | 状態 | 内容 |
|----------|------|------|
| **R1′-A** | **本仕様の詳細対象・第一波必須** | 入力スキャン、候補短絡、人の確定、作品取り込み、カード／ログ紐づけ、差分ログ |
| **R1′-B** | 境界のみ（§11） | 振り返り章（画面／PDF） |
| **R1′-C** | 境界のみ（§11） | 蓄積ログの外部分析用エクスポート（NotebookLM 等） |

### 3.2 R1′-A に含めないもの

- 毎日 20→1 の速い輪（R4′）
- クラウドアルバム入力（R5′）
- 自前 RAW 現像・アプリ内本格補正
- 印刷業者入稿
- 種写真からの自動ストーリー補完の本実装（R3′。種からの入口の UI 予約は可）
- ★スコアのみによる自動最終選別
- LINE／マルチユーザー／課金

## 4. 用語

| 用語 | 意味 |
|------|------|
| LibraryUnit | 短絡の対象単位。月フォルダまたはイベント・サブフォルダ |
| SourceAsset | オリジナル画像（非破壊。アプリが内容を書き換えない） |
| ShortlistCandidate | AI または人が扱っている候補1件 |
| Work | オリジナルとは別に保存する「作品」画像とそのメタ |
| DialogueTrace | 作品に紐づく対話痕跡（カード、ノート、ログ、コメント等） |
| DecisionDelta | ある短絡セッションにおける、AI 提案と人の確定の差分記録 |
| 回収 | 提案から漏れたが、人が気になって残す操作（recovered） |

## 5. ドメインモデル

### 5.1 LibraryUnit

| フィールド | 型・制約 | 説明 |
|------------|----------|------|
| `id` | 文字列 | 安定ID（パスの相対表現など） |
| `kind` | `month` \| `event` | 月またはイベント |
| `path` | 絶対パス | 対象フォルダ |
| `label` | 文字列 | 表示名。イベントは `_` 以降 |
| `ym` | `YYYYMM` | 所属月 |

フォルダ規則（構想どおり）:

- 月: 親フォルダ名 `YYYYMM`
- イベント: `YYYYMMDD_短い名前`（開始日＋`_`＋名前）
- パターン不一致のサブフォルダはイベント単位にしない

### 5.2 SourceAsset

| フィールド | 説明 |
|------------|------|
| `path` | オリジナルファイルパス |
| `file_name` | ファイル名 |
| `captured_at` | EXIF `DateTimeOriginal` 優先（既存 `scanner.py`） |
| `suffix` | `.jpg` / `.jpeg` / `.png` / `.heic` / `.heif` 等（`SUPPORTED_IMAGE_SUFFIXES`） |

### 5.3 ShortlistCandidate

| フィールド | 説明 |
|------------|------|
| `source_id` | SourceAsset 参照 |
| `session_id` | 短絡セッション ID |
| `priority` | 数値。小さいほど優先（コア案が上） |
| `tier` | `core` \| `maybe`（コア／迷い枠） |
| `status` | `proposed` \| `kept` \| `rejected` \| `recovered` |
| `reason_brief` | AI による短い提案理由（言語化支援。見るだけ可） |
| `signals` | 用いた信号の要約（実装用。ユーザーに生データ強制表示はしない） |

状態遷移:

```text
proposed --> kept
proposed --> rejected
（非提案の Source） --> recovered --> kept 相当として作品化対象
kept --> rejected（人が取り消す）
rejected --> kept / recovered（人が戻す）
```

### 5.4 Work

| フィールド | 説明 |
|------------|------|
| `id` | 作品 ID |
| `source_id` | 元 SourceAsset |
| `image_path` | 作品画像の保存パス（オリジナルとは別） |
| `rendition` | `sooc` \| `jpeg_edit` \| `raw_export` |
| `external_source_path` | 取り込んだ外部ファイルの元パス（任意・監査用） |
| `created_at` | 作成日時 |
| `user_comment` | 撮影者コメント（任意） |
| `keywords` | 文字列配列（任意） |

`rendition` の意味:

| 値 | 意味 | R1′-A での入れ方 |
|----|------|------------------|
| `sooc` | JPEG/HEIF 撮って出し | オリジナルからコピー、または同内容の指定ファイル |
| `jpeg_edit` | JPEG 補正後 | 外部アプリ成果を選択してコピー |
| `raw_export` | RAW 現像 JPEG | 外部アプリ成果を選択してコピー |

### 5.5 DialogueTrace

| フィールド | 説明 |
|------------|------|
| `work_id` | 対象作品 |
| `card_path` | 講評カード PNG（既存生成物） |
| `note_path` | 個別 Markdown ノート |
| `mode` | `compact` \| `full`（既存講評モード） |
| `lens` | `self`（固定） |
| `user_comment` / `keywords` | Work と共有または同期 |
| `ai_wording` | 短絡理由や追加の短い言葉（修正可・しなくても可） |
| `user_reaction` | 任意。例: `agree` \| `disagree` \| `unset`（「そう思う／そうではない」） |

生成経路: 既存の `critique_engine` → `generate_critique_card` → `DesktopLogManager.save_analysis_result` を **作品画像** に対して実行する。月次／年次ログへの追記方針は既存に合わせ、作品ファイル名をキーにする。

### 5.6 DecisionDelta

| フィールド | 説明 |
|------------|------|
| `session_id` | 短絡セッション |
| `library_unit_id` | 対象 |
| `proposed_core_ids` | コア提案の source 一覧 |
| `proposed_maybe_ids` | 迷い枠一覧 |
| `kept_ids` | 人が残した一覧 |
| `rejected_ids` | 却下一覧 |
| `recovered_ids` | 回収一覧 |
| `completed_at` | 確定時刻 |

R2′（差分が提案に効く）の入力種として保存する。R1′-A では **保存と参照ができれば合格**（学習ロジックの本実装は R2′）。

### 5.7 ShortlistSession

| フィールド | 説明 |
|------------|------|
| `id` | セッション ID |
| `library_unit_id` | 対象 |
| `target_keep_count` | 目安件数（週 20／イベント 40 など。変更可） |
| `status` | `running` \| `awaiting_review` \| `completed` \| `cancelled` |
| `created_at` | 開始時刻 |

## 6. 主要フロー（R1′-A）

```text
[1. 単位選択]
  ユーザーが月またはイベントフォルダを選ぶ
        ↓
[2. スキャン]
  SourceAsset 一覧を列挙（scanner の拡張子規則）
        ↓
[3. 候補提案]
  AI／規則で ShortlistCandidate を生成（core + maybe）
  各候補に reason_brief（言語化支援）
        ↓
[4. 人の確定]
  kept / rejected / recovered を操作
  必要なら AI 文への反応（agree/disagree）や修正
        ↓
[5. 作品取り込み]
  確定分について rendition を選び、Works へコピー保存
        ↓
[6. 対話痕跡]
  作品ごとに講評カード・ノート・ログを生成／更新
        ↓
[7. 差分保存]
  DecisionDelta を書き出し、セッション完了
```

### 6.1 エラー方針

- 1枚の失敗でセッション全体を止めない（既存 GUI バッチの独立 `try/except` 思想）。
- オリジナルファイルの削除・上書きは行わない。
- 外部現像ファイルが見つからない場合は、その作品だけ保留し、他は継続。

### 6.2 再実行

- 同一 LibraryUnit で短絡をやり直せる。
- 既存 Work がある場合は上書き確認を求める（黙って消さない）。
- 講評の再生成は既存の処理済み判定思想と整合させる（作品ファイル名キー）。

## 7. 候補提案の原則

### 7.1 やってはいけないこと

- 現行の揺れる ★ スコア**だけ**で最終候補を決めること（`PHASE_D_FINDINGS.md`）
- 「良い写真ランキング」として提示すること
- 人が確定する前に候補外を削除すること

### 7.2 使う信号（R1′-A の方針）

実装詳細は後続でもよいが、仕様上は次を組み合わせる。

| 信号 | ねらい |
|------|--------|
| 近傍重複・連写の圧縮 | 似たコマの冗長を減らす |
| 時間／イベント内の散らばり | 一日・場面の偏りを抑える |
| 光・陰影・反射などの視覚兆し | レンズの「感情の陰影」方向 |
| 人物のしぐさ・視線（いる場合のみ） | 物語の気配。無人物への擬人化禁止 |
| 枠取り・余白の明確さ | 眼差の輪郭方向 |
| ユーザー過去の kept/recovered（あれば） | R2′ へつなぐ差分の芽 |

### 7.3 提示の形

- **core**: 目安件数に近い本候補（例: イベント 40 前後）
- **maybe**: 迷い枠（多め・優先度付き）。初期は厚めに出してよい
- 各候補に **短い reason_brief**（AI 言語化）。ユーザーは見るだけでもよい
- 反応 `agree` / `disagree` を任意で残せる（強制しない）

### 7.4 性能の目安（第一波）

- 400 枚スキャンの列挙はローカルで即座
- 提案生成はバッチで可。進捗表示と中断ができること
- コスト増大を避けるため、全枚フル講評（Phase2）を短絡段階では走らせない。短絡は軽量な提案理由に留め、フルカードは **作品確定後** に行う

## 8. UI 方針（デスクトップ）

### 8.1 配置

- 現行の講評バッチ GUI（`app_gui.py`）は維持する。
- 深い輪は **別モードまたは別ウィンドウ／別起動導線** として追加する（既存バッチを壊さない）。
- 新フレームワークへの全面移行はしない。

### 8.2 画面の仕事（R1′-A）

1. LibraryUnit 選択（フォルダ）  
2. 短絡実行と進捗  
3. 候補レビュー（サムネ＋ reason_brief ＋ kept/reject/recover）  
4. 作品取り込み（rendition 選択とファイル指定）  
5. 痕跡生成の実行とログ表示  
6. セッション完了サマリ（kept 数、差分の有無）

ダッシュボード化（統計カードの羅列、ヒーロー過多）はしない。  
**確認リストと一枚ずつの対話**が主UI。

### 8.3 設定

- `~/.photo_ai_config.json` の既存キーは壊さない。
- 深い輪用キーを追加する（例: 最後に開いた LibraryUnit、カードテーマ、目安 keep 数）。キー名は実装時に単一ソース化する。

## 9. 保存場所（規約）

LibraryUnit ルートを `{unit}` とする。オリジナル直下は汚しすぎないよう、規約サブフォルダにまとめる。

```text
{unit}/                          # 月またはイベント（オリジナル置き場）
  （既存の撮影ファイル群）
  _lumina/
    sessions/
      {session_id}.json          # ShortlistSession + candidates + DecisionDelta
    works/
      {work_id}_{stem}.jpg       # 作品画像（例）
      {work_id}.json             # Work メタ（comment/keywords/rendition 等）
    traces/
      （カード・ノートをここに置くか、既存月次構造と併用するかは実装で一本化）
```

### 9.1 既存ログ構造との関係

現行デスクトップは月フォルダ直下に次を作る。

- `{ym}写真分析ノート/`
- `{ym}評価カード/`
- `{ym}写真分析ログ.txt`
- `{ym}処理ステータス.txt`
- 親に `写真分析ログ_{year}.txt`

R1′-A 方針:

- **Work に対する講評**は、可能な限り既存 `DesktopLogManager` の出力契約を再利用する。
- イベント・サブフォルダを単位にしたとき、ログの親を月に集約するかイベントに持つかは実装詳細で決めるが、**仕様上の要件**は「作品からカードとノートに辿れる」「月次またはイベント次で一覧できる」こと。
- `_lumina/works/*.json` に `card_path` / `note_path` を必ず記録し、紐づけの単一参照点とする。

### 9.2 非破壊

- SourceAsset の削除・改名・上書き保存をアプリから行わない（ユーザーが Finder 等で行うのは対象外）。
- 作品はコピー保存。外部現像の原本も上書きしない。

## 10. 受け入れ条件（R1′-A）チェックリスト

| # | 条件 | 合格の目安 |
|---|------|------------|
| A1 | イベント `YYYYMMDD_名前` を単位に選べる | パターン外サブフォルダは単位に出ない |
| A2 | 約 400 枚をスキャンし候補を提示できる | core と maybe が分かれて見える |
| A3 | 人が kept / rejected / recovered できる | 最終 roughly 40 枚前後に整えられる |
| A4 | 提案理由文を読める | 未修正のままで完了できる |
| A5 | sooc / jpeg_edit / raw_export のいずれかで作品保存できる | オリジナルが変わっていない |
| A6 | 作品にカードとノートが紐づく | `_lumina/works/*.json` からパスを辿れる |
| A7 | DecisionDelta が残る | proposed と kept/recovered/rejected を後から比較できる |
| A8 | 1枚失敗しても他が続行できる | エラーがログに残りセッションが死なない |
| A9 | 既存講評バッチ GUI が回帰しない | 従来どおりフォルダ一括講評ができる |

## 11. R1′-B / R1′-C の境界（詳細は後続仕様）

### 11.1 R1′-B 振り返り章

## 12. テスト方針

| 種類 | 内容 |
|------|------|
| オフライン自動 | フォルダ規則判定、候補状態遷移、DecisionDelta の整形、パス規約、設定キー後方互換 |

## 13. 実装時のモジュール方針（予告・仕様レベル）

対症療法的な分岐を避け、次の単一責任に寄せる（規則1: 3段階レビュー）。

| 仮モジュール | 責任 |
|--------------|------|
| `library_unit.py`（仮） | 月／イベントパスの識別と列挙 |
| `shortlist_engine.py`（仮） | 候補提案（信号・tier・reason_brief） |
| `work_store.py`（仮） | 作品コピーとメタ JSON |
| `delta_log.py`（仮） | DecisionDelta の読み書き |
| 既存コア | 講評・カード・DesktopLogManager・scanner |

GUI は上記を呼び出すだけにし、提案ロジックをウィジェットに埋め込まない。

## 14. 次の工程

1. 本仕様（特に R1′-A）のオーナー確認  
2. 実装タスク分解（library_unit → shortlist → review UI → work_store → trace）  
3. オフラインテストの追加方針を実装 PR で具体化  
4. R1′-B/C は A が日常で回ったあとに個別仕様化
