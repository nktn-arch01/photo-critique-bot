## 0. メタデータ一次ソース（**運用確定**・2026-08-11）

**JPEG メタと DxO の同期は検証 PASS。`.dop` / `.xmp` は使わない。**

| 用途 | 一次ソース | 明示的に使わないもの |
|------|------------|----------------------|
| **短絡**（Rating / 説明） | **JPEG 内**の Rating + Description（IPTC/XMP） | `.dop` サイドカー、`.xmp` サイドカー |
| **分析（講評）** | **画（JPEG 画素）** ＋ **撮影 EXIF**（`DateTimeOriginal`、絞り、SS、ISO、焦点距離、カメラ／レンズ等） | RAW 現像パラメータ（露出／WB／トーン等のスライダー値）。`.dop` / `.xmp` の現像レシピ |

補足:

- 短絡バッチは JPEG に Rating／Description を**書き込む**（現行コードは書き込みなし → 実装で追加）。
- 講評・短絡の読み取りも、同期成立後は **JPEG を正**とする（現行の `.dop` 優先 Rating／意図は移行完了後に廃止またはフォールバックのみ）。
- `_dev.jpg` を講評する場合も一次ソースは同じ（そのファイルの画素＋埋め込み撮影 EXIF）。現像で変えた見え方は**画を正**とし、EXIF は「撮影時の記録」として扱う（画素と設定の不一致があり得ることを仕様上許容し、プロンプトで画優先を明示する方向）。
- Preset 名など `.dop` 固有情報は、第一波の必須入力にしない。

### 0.1 IPTC 同期検証チェック（A10）

詳細手順・結果表: [`IPTC_SYNC_VERIFICATION.md`](IPTC_SYNC_VERIFICATION.md)

合格条件:

1. exiftool／検証スクリプトで JPEG に Rating と Description を書く → **ファイル再読取 PASS（実施済）**  
2. DxO PhotoLab で同じ Rating／説明が見える → **オーナー手動**  
3. （努力）DxO 側変更がファイルに残る  

書き込みタグ契約（ファイル側）:

| 目的 | タグ |
|------|------|
| Rating | `Rating` / `XMP:Rating` / `RatingPercent` |
| 説明 | `ImageDescription` / `XMP-dc:Description` / `IPTC:Caption-Abstract` |

不合格時（DxO UI）: `.dop` 読みフォールバックの要否を再検討。  
**現状:** 不合格には該当せず（§B9 PASS）。

## 1. 目的と成功条件

### 1.1 目的

ミラーレス派ユーザー（当面はオーナー本人）が、**週次およびイベント単位**の写真群に対して、

1. 本アプリの **バッチ短絡**が JPEG に Rating／説明を書き込み、  
2. **DxO 等の日常アプリ**で一覧確認・Rating 修正・現像・Works への書き出しを行い、  
3. 確定作品（主に `{stem}_dev.jpg`）に既存の Lumina Notes（カード・分析ログ）を紐づけて **対話痕跡** を残す  

ことで、ワークフローを大きく変えずに、あとから未来の自分が読み返せる素材を蓄積する。

北極星のうち、本仕様が担うのは主に **深い輪**。  
中心の往復（残す→見返す→言葉にする→もう一度見る）を、週／イベントで回す。

### 1.2 縮約の目安（最終）

| 単位 | 入力の目安 | 確定の目安（Rating 3 または 4） |
|------|------------|--------------------------------|
| 週 | 約 200 枚 | 約 20 枚 |
| 月／イベント | 約 400 枚 | 約 40 枚 |

途中段の目安は §6。最終は人が DxO 等で決める。

### 1.3 成功条件（R1′-A）

1. バッチが M1→M2→M3 を実行し、対象 JPEG に Rating／説明が書き込まれる  
2. DxO 等で Rating 一覧を確認・修正できる（H3。同期は §B9/B10 で PASS）  
3. 本アプリは **Works へのコピー機能を持たない**（書き出しは DxO 等）  
4. Works（またはユーザーが置いた確定フォルダ）上の `{stem}_dev.jpg`（なければ撮って出し）にカード／ノート／ログを付けられる  
5. バッチ結果の監査ログ（DecisionDelta 相当）が残る

## 2. ユーザーストーリー

### US-1 週末バッチ → DxO で確定

週末、週のフォルダに対して本アプリの短絡バッチを一度走らせる。JPEG に Rating と説明が付く。いつもどおり DxO を開き、Rating を見て直し、必要ならファイル削除は任意で行う。Rating 3/4 を残し、オリジナル側で RAW 現像して `_dev.jpg` を出し、DxO から Works へ書き出す。その後、本アプリで対話痕跡（カード等）を付ける。

### US-2 イベントも同じ

イベント `YYYYMMDD_短い名前` でも同じ（およそ 400→40）。

### US-3 言葉は「説明」に載る

M2/M3 の reason_brief が IPTC 説明に入り、DxO 上で読める。納得しなくてもよい。必要なら人が直す。

### US-4 二重管理をしない

Works に RAW や「同名の競合 JPEG」を置かない。確定コマの撮って出しと `_dev.jpg` だけが Works に来る（DxO 側の操作）。

## 6. 段階短絡フロー（R1′-A）

```text
[本アプリ バッチ]
  単位選択 → スキャン（主に JPEG。HIF 対応は検証後）
  → M1 機械 → Rating=1（不合格は 0）
  → M2 アンテナ → Rating=2 + 説明[M2]
  → M3 多様性 → Rating=3 or 4 + 説明[M3]
  → 監査ログ保存

[ユーザー / DxO 等]
  → H3 Rating 一覧確認・修正（0〜4）
  → 任意で Rating=0 相当ファイルを削除
  → オリジナル側で RAW 現像 → {stem}_dev.jpg
  → W: Rating 3/4 を Works へ（撮って出し.jpg と _dev.jpg。RAW は送らない）

[本アプリ]
  → Works（または指定フォルダ）の確定画像に対話痕跡
```

### 6.1 段の定義

| 段 | 週の目安 | 性質 | Rating / 説明 | 実行場所 |
|----|----------|------|---------------|----------|
| **M1 機械** | 200→≈180（約80%+） | 消去法＋意図保護 | 合格=1、不合格=0 | 本アプリバッチ |
| **H1** | — | — | — | **不要** |
| **M2 アンテナ** | 180→≈50（約25%） | 相対熱量 | 合格=2、説明に [M2] | 本アプリバッチ |
| **H2** | — | — | — | **不要** |
| **M3 多様性** | 50→≈20（約10%） | 余白＋上位 | 余白=3、上位=4、説明に [M3] | 本アプリバッチ |
| **H3 確認** | 最終調整 | 人 | 全 Rating を一覧修正。0=除外 | **DxO 等** |
| **W 作品** | 3/4 のみ | 書き出し | 撮って出し＋`_dev.jpg`（RAW なし） | **DxO 等** |
| **T 痕跡** | 確定画像 | 対話 | カード／ノート／ログ | 本アプリ |

イベント 400 も同比率ガイド（例: →≈320→≈100→≈40）。

### 6.2 3観点との対応

| 観点 | 担当 | 原則 |
|------|------|------|
| 機械選別 | M1 | 失敗は 0。低速SS・開放・意図的アンダー等は保護し 1 側へ |
| Lumina Notes 観点 | M2 | 5軸相対熱量。★絶対ゲート禁止 |
| 多様性調整 | M3 | 余白=3、上位=4。執着の癖を優先しうる |

実装: [`shortlist_diversity.py`](../shortlist_diversity.py)

- 入力 Rating≥2。残す比率 `keep_ratio`（既定 0.40 ≒ 最終10%ガイド）
- 画素の色相・輝度ビン＋軽量 Vision（quality / attachment / tags）
- 貪欲法で品質と多様性を両立。残したうち `top_ratio` を Rating=4、残りを 3
- 非残しは Rating=2 のまま。語彙は `DiversityConfig.tag_vocab`

#### 6.2.1 使用上の注意（M3）

- 似たコマが並ぶ単位では、品質が少し低くても違うタグ／色のコマが残りやすい。
- 執着ブーストで「偏り」の強いコマが上位に入りうる（仕様どおり）。
- タグは既定語彙外を採用しない。語彙は設定で差し替え。
- H3 で 3/4 の入れ替えは正規運用。


### 6.3 M2 の5軸（既存レンズ）

`framing` / `sensitivity` / `story` / `technical` / `sense`  
表示名は `critique_lens.py` に従う。選抜は相対熱量（ピーク軸・共鳴）。★5必須は禁止。

実装: [`shortlist_antenna.py`](../shortlist_antenna.py)

- 軽量 Vision（短い JSON スコアのみ。Phase2 なし）
- 熱量 = ピーク＋平均＋共鳴（閾値以上の軸数）。バッチ内上位を合格（`pass_ratio` 既定 ≈0.28）
- 合格: Rating=2 ＋ `[M2]` 理由。非合格は Rating=1 のまま（0 には落とさない）
- Rating<1 はスキップ

#### 6.3.1 使用上の注意（M2）

- 合格数は単位ごとの**相対**。弱いセットでも上位は 2 になる（絶対★ゲートなし）。
- Vision API が必要（オフライン選抜ロジックは `score_fn` 差し替えでテスト可）。
- 理由文は短い要点。人が H3 で直してよい。


### 6.4 M1 の意図保護（閾値は実装詳細）

- 低速シャッター、開放寄り、意図的アンダー（RAW のハイライト保護を含む）を機械不合格から守る余地を持つ。
- 実装: [`shortlist_mechanical.py`](../shortlist_mechanical.py) の `MechanicalConfig`（`slow_shutter_sec` / `open_aperture_max_f` / `intentional_under_ev` 等）。ブレ指標は Laplacian 分散。

#### 6.4.1 使用上の注意（想定される誤判定）

M1 は「明らかな失敗」の足切りであり、表現意図の理解はしない。**Rating 0 になっても H3（DxO 等）で 1 以上に戻せばよい**（物理削除はしない）。

| 撮影の例 | 起きうること | 理由（現行ロジック） |
|----------|--------------|----------------------|
| **星空・夜景（画面の大半が暗い）** | 不合格（`fail_underexposed`）になりうる | 平均輝度／黒クリップが大きいと黒つぶれ判定。ただし **低速 SS・開放・露出補正アンダー** のいずれかが EXIF にあれば意図保護で合格側 |
| **星空でも長秒露出の EXIF が残っている** | 多くは合格側 | `ExposureTime ≥ 1/30s`（既定）で `protect_slow_shutter` |
| **流し撮り・ICM（意図的な強いブレ）** | 不合格（`fail_blur`）になりうる | 画面全体が柔らかいとブレ判定。**SS が既定より速い**（例: 1/60 以上）かつ開放・アンダー保護も無いと救われない |
| **流し撮りで低速 SS が EXIF に残る** | 多くは合格側 | 同上、低速 SS 保護 |
| **霧・吹雪・白壁のハレーション** | 不合格（`fail_overexposed`）になりうる | 白飛びは意図保護の対象外（現行） |
| **シルエット（露出補正なし）** | 不合格（黒つぶれ）になりうる | 暗い画面＋保護 EXIF なし |
| **ソフト焦点・強い拡散・被写体ピンボケで背景はテクスチャ多め** | 不合格にも合格にもなりうる | ブレ指標は画面全体。主題の合焦は見ていない |
| **EXIF が欠けた書き出し JPEG** | 意図保護が効かない | 保護は撮影設定数値依存。欠落時は画素指標のみ |

運用メモ:

1. **H3 で拾う前提** — 星空・流し撮り・表現的ブレ／アンダーは、0 のまま残して DxO で Rating を戻すのが正規ルート。  
2. **保護の頼れる信号** — 長秒・開放・マイナス補正がファイルに残っていること。現像書き出しで EXIF を落とすと誤って 0 になりやすい。  
3. **約 80%+ 合格はガイド** — 夜だけ／パンだけが多い単位では合格率が下がってよい。閾値は `MechanicalConfig` で調整可能（将来の設定 UI／ファイル化は T6 以降）。  
4. **逆方向の取りこぼし** — 軽いピンボケでもテクスチャが強いと合格することがある（主題未合焦の見逃し）。最終判断は H3。


### 6.5 コスト分離

- M2/M3 は軽量パス。フル講評（Phase2）は短絡バッチで走らせない。
- フルカードは **T（痕跡）** で、Works 上の確定画像に対して行う。

### 6.6 エラー方針

- 1枚失敗でバッチ全体を止めない。
- 画素データの上書き・削除はしない。
- メタデータ書き込み失敗はログし、当該ファイルをスキップ。

```text
  IMG_0001.ORF
  IMG_0001_dev.jpg               # 現像（オリジナル側でも可）
  _lumina/
    sessions/{session_id}.json   # バッチ監査

  IMG_0001.jpg                   # 任意

  （本アプリはここを読んで痕跡生成。コピーはしない）
```

カード／ノートは既存月次構造と併用可。紐づけメタは `_lumina` または works 横の JSON で辿れること。
